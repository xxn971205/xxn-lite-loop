# 档位和升档

| 你要推进的工作 | 角色与 Git 台账 | 合入方式 |
| --- | --- | --- |
| L1 个人小需求 | 一个追踪 Issue 和一个主控。默认手动推进，每个变更单有独立终审。 | 单变更单由本人合回主干。拆多个变更单且建了独立需求基线时，可明确开启低风险自动合入基线。 |
| L2 个人复杂需求或多仓 | 一个主台账和业务子 Issue，主控与小巡检各自有会话和定时任务。 | 按确认配置和终审分流合入需求基线，公共分支由本人处理。 |
| L3 多人并行 | 总台账、各人小台账、子 Issue 和一个升级 Issue。主研发有独立调度和大巡检，每位开发者有主控和小巡检。 | 需求基线由主研发账号处理，调度通过门禁合入符合条件的变更，高风险和公共分支交主研发本人。 |

实际周期、工作时段、检查阈值和通知窗口读 `loopctl.mjs config-resolve --project <slug> --tier <档位>`。进行中的需求以确认后写入的运行态为准。角色唤醒执行 `tick`，队列发送执行 `notify`。L3 公共门禁和阶段参数由主研发通过 PR/MR 更新。成员可在门禁范围内配置个人偏好。

## 工作推进顺序

| 阶段 | 做什么才往下走 |
| --- | --- |
| P0 需求澄清 | 阻断疑问都已裁决。 |
| P1 方案设计 | 设计、初版契约和验收方案确认，建首批子 Issue。 |
| P2 地基与契约 | 地基验证后合入基线，契约与文件归属明确，L3 各槽位业务级五项汇总获确认。 |
| P3 开发 | 每个业务子 Issue 细化并确认后，拆 1–3 个可独立验收的 PR/MR。全部合入基线并完成集中验证。 |
| P4 联调、测试与上线 | 联调和缺陷复测通过，人合入并部署，再拆架。 |

本人或 L3 主研发决定切阶段。L1/L2 已明确的需求可从匹配的阶段起步。

## 平滑升档

1. 执行 `loopctl.mjs upgrade --req <slug> --to L2|L3` 出计划，确认新增与复用对象后再执行。按 L1、L2、L3 的顺序升档。
2. L1 升 L2 时，原追踪 Issue 成为主台账，历史评论和合入链接保留。把未完成工作拆成业务子 Issue，补标签，增加主控定时任务和独立小巡检。从本档开始按子 Issue 计划交接。
3. L2 升 L3 时，原主台账成为总台账。为主研发建个人小台账和升级 Issue，补契约与文件归属，未分配子 Issue 标槽位等同事认领。给主研发增加独立调度与大巡检，个人主控和小巡检改绑个人小台账。日报由大巡检按设置出队。
4. 按计划登记实际台账编号和宿主任务回执，运行 `upgrade --req <slug> --to L2|L3 --apply --issue-map <json> --results <json>` 落盘。外部创建失败时沿原计划补齐后重试。L3 同事由总台账链接进入 [加入流程](lifecycle.md#加入已有-l3)。
