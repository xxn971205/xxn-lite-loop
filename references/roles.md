# 角色执行规范

项目或个人有工程规范时，怎么写代码、怎么测、怎么审以工程规范为准；本文件只管流程要求。主控规则见 [主控](controller.md)，派审与合入门禁见 [独立终审与合入](review-and-dispatch.md)。

<a id="common"></a>
## 共同底线

所有被派出的执行角色都须遵守：

1. 读本节、对应角色节与任务说明列出的规范。按任务说明的交付标准执行。
2. 从远端基线读规范、契约与代码，并在产出里写明所用基线 SHA。
3. 未跑写「未验」，只跑了一部分写「未完成」。模型、网关或额度故障记为环境问题。
4. 未查清的问题先定位到明确阻塞点，不直接转给人去测。
5. 只在分配给自己的工作区与分支内操作。
6. 凭据不进输出、日志、评论与证据；任务说明或本次已提供的输入不重复向人索要。
7. 只交付任务说明要求的产出，不在本角色之外动手改动台账、分支或代码。

<a id="planner"></a>
## 拆分

1. 输出 [业务子 Issue 五项](templates.md#业务子-issue-五项) 和「与确认范围的差距」（无差距也写「无」）。
2. 设计依赖的现有能力、入口与字段类型，必须在基线源码或真实元数据中核实并附链接，不凭推测写。
3. 每个变更单须可独立验证并有真实消费方。接口声明与实现在同一变更单交付。
4. 写清范围边界与必要的冒烟提示，验收者按确认范围独立出题。

<a id="coder"></a>
## 开发

1. 交付必须写明：分支、候选 head SHA、所用基线 SHA、按项目命令跑出的证据（命令、退出码、证据层级）与未验项；建单要求见 [送审前](review-and-dispatch.md#送审前)。
2. 不删除仍有效的测试换通过，不加入与确认范围冲突的限制。
3. 公共契约、他人归属文件与共享基础设施的已有内容不在业务单里顺手改：L3 走 [L3 升级串](templates.md#l3-升级串)，L1/L2 在交付里单列交人确认。
4. 返修按 [送审前的分支规则](review-and-dispatch.md#送审前) 更新候选。终审进行中需改动时先通知主控。

<a id="self-reviewer"></a>
## 自审

1. 自审结论附实际跑过的测试或逐步核对的源码调用链。
2. 结论只交给主控作送审参考，不代替独立终审，不写进合并依据，也不直接修改变更单标签。

<a id="final-reviewer"></a>
## 终审

1. 只审派审固定的 head（`headSha`），且作者与本需求主控不得担任终审；派审登记与 `verdict` 命令见 [独立终审](review-and-dispatch.md#独立终审)。
2. 每次终审结论必须按三级给出问题分级，三级都须带「入口：」（已支持的业务入口与触发路径）和「证据：」（源码调用链或运行复现）：
   - **P0 阻断**：主路径不可用，数据错误或丢失，安全或权限漏洞，契约破坏导致上下游出错。
   - **P1 严重**：用户能触发的功能缺陷或错误结果，漏了必需的校验，测试证明不了本次改动。
   - **P2 一般**：次要边界、可维护性、结构、体验细节。能从入口触发，但影响有限。
3. 打回时按行首编号或 `- ` 分条。每条 `--must-fix` 须以 `【P0】`、`【P1】` 或 `【P2】` 开头（也接受 `P0：` 等写法，脚本统一归一成 `【P0】`），并填实「入口：」和「证据：」。缺等级、缺项或空字段脚本拒收。可选的 `--remaining`（遗留建议）仅允许 P2，同样须带等级、入口和证据，不阻塞合入。
4. 做不到从已支持业务入口触发的疑点只写成「线索」，不评级、不进 `--must-fix`、不打回；极罕见但后果严重的写清依据交人裁决是否列为必改。
5. 前 2 轮为深审，问题尽量一次挖透，P0/P1/P2 均可打回；普通复审只核上轮必改项与直接影响面。累计打回次数达到熔断阈值（`rejectFuseCount`，默认 2）后，派审带 `fullReReview` 标记时仍执行全量复审，但只就 P0、P1 打回——必改项不得出现 P2，P2 改写到 `--remaining`；只剩 P2 时给「通过」并将 P2 写入 `--remaining`，通过后仍交人裁决。
6. 逐项给出「通过 / 不通过 / 不适用 / 未验证」判断。六项固定风险用 `verdict --risk` 标记命中情况，项目追加风险写在审查结论里。

<a id="acceptor"></a>
## 验收者

1. 验收环境、入口与核对方法读工程档案 `acceptance.guide` 指向的项目文件。
2. 按确认范围独立出题，不用拆分阶段写的验收清单。验收题目由验收者持有。独立算出预期，再核对实际产物与副作用。
3. 按确认范围逐条给证据并标明层级（真实链路 / 替身 / 截图自报）；替身、截图或自报不能证明真实链路；受控替身验边界、真实链路验主路径，不硬造极端输入。
4. 验不了的写「未验」，跑一半写「未完成」，不交「通过」；复用旧证据前写清源码、依赖、配置、构建与输入均未受影响。
5. 发现失败先定类（产品约定 / 实现 / 测试 / 环境）再交主控，不笼统退回开发。

<a id="retro"></a>
## 复盘

1. 仅在用户要求时执行，不自动触发。
2. 依据归档的 `teardown.metrics`、台账与【裁决】原文取证，不凭印象总结。
3. 输出 ≤5 条建议，每条标注归因层（`lite-loop 机制` / `个人配置` / `工程规范` / `模型` / `需求本身`）与对应依据。
4. 建议交用户逐条确认后再改动配置、规范或脚本，不未经确认直接落改。
